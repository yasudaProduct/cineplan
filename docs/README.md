# docs/ — ドキュメント索引

映画館はしごスケジューリングサービスのドキュメント一式。Claude Code での開発時は、着手するタスクに対応するドキュメントを必ず読み込んでから実装すること。

## フォルダ構成と分類ルール

ドキュメントは「内容の種類」ではなく**更新のライフサイクル**（いつ・どう更新するか）で 4 フォルダに分類する。新しい文書を置くとき・既存文書を直すときは、この表の更新様式に従う。

| フォルダ | 役割 | 更新様式 |
|---|---|---|
| `spec/` | **設計マスタ**。現在のシステムの姿を記述する生きた文書 | 上書き更新。**実装と食い違ったら文書を先に直す義務がある**（文書が正） |
| `plan/` | **計画**。ある時点の意図（ロードマップ・進行手順） | フェーズ完了後は履歴として凍結し、書き直さない |
| `decisions/` | **設計判断の記録**（ADR） | **追記専用**。覆すときは Supersedes 付きの新 ADR を追加する。既存 ADR は消さない |
| `guides/` | **手順書**。人間（オーナー）が手で実行する作業手順 | 手順が変わったら更新 |

### 採番ルール

- 文書番号は**フォルダ内の連番**（spec: 01〜、plan: 01〜、guides: 01〜）。番号だけでは一意にならないため、**引用は必ずフォルダ付き**で `docs/spec/08 §3` / `spec/08 §3` の形式にする。新規文書はそのフォルダの次番号を採番する。
- ADR は 4 桁の通し番号（1 判断 = 1 ファイル）。引用は `ADR-00NN` 形式。
- **旧番号との対応（2026-07-29 再番）**: 再番前はフォルダをまたいだ通し番号 01〜16 だった。`decisions/` 内の ADR 本文や過去のコミット・PR に残る `docs/NN §M` 形式の引用は旧番号を指す（追記専用のため書き換えていない）。対応は次のとおり（01〜08 は spec/ の同番号のまま）:

| 旧 | 新 | | 旧 | 新 |
|---|---|---|---|---|
| 09 | `plan/01_roadmap.md` | | 14 | `spec/11_environments-deploy.md` |
| 11 | `spec/09_d1-implementation.md` | | 15 | `spec/12_folder-structure.md` |
| 12 | `spec/10_dp-implementation.md` | | 16 | `guides/01_human-setup-guide.md` |
| 13 | `plan/02_claude-code-kickoff.md` | | 10 | `decisions/`（旧 10_adr/） |

### 設計判断の載せ先基準

- **「今こうである」**（現行の規範・制約・挙動）→ `spec/` の該当文書に書く。
- **「なぜそうしたか・何を捨てたか」**（経緯・理由・非採用案）→ `decisions/` に ADR として書き、spec 側からは `ADR-00NN` で参照する。
- 迷ったら: その記述を更新するとき「過去の記録の書き換え」に感じるなら decisions、「仕様の更新」に感じるなら spec。

## ドキュメント間の優先順位（矛盾時）

1. `spec/02_glossary.md`（命名・用語） — すべてに優先
2. `spec/01_requirements.md`（何を作るか）
3. `spec/03`〜`07`（どう作るか） — 実装と食い違ったらドキュメントを先に直してから実装を直す
4. `spec/09`〜`10`（実装詳細） — 論理設計（spec/03・spec/05）と食い違ったら、まず両者どちらが正しいか判断して片方を直す。期待値（spec/10 §7）は検算済みのため、原則こちらを正とする

## 実装時の不変条件（全ドキュメント共通）

- 取得した上映スケジュールは内部ロジック専用。劇場×日付の上映一覧を返す API・画面を作らない。
- 先方サイトへのアクセスは最小限（**1日1セッション原則・1セッション最大10ページ**・再処理は R2 スナップショットから）。
- zod スキーマ（packages/shared）が型の単一の真実。API/DB/フロントで別定義を作らない。
