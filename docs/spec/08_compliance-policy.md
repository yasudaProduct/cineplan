## 0. Claude Code への指示（最初に読むこと）

このプロジェクトの取込サービスを実装・改修する際、以下は**禁止事項**であり、パフォーマンスや利便性を理由に自己判断で導入・変更してはならない。変更が必要と考えた場合は実装せず、人間に確認を求めること。

- ❌ 同一サイトへのリクエスト間隔を 5秒未満に短縮すること
- ❌ 1劇場への**取得セッション**（＝定時 Cron 1回分の取込）を1日1回より増やすこと（レビュー再取得を除く）
- ❌ 1セッションで取得するページ数の上限（`MAX_FETCH_DAYS` = 10ページ／劇場）を引き上げること、または複数日取得を劇場ごとの設定（`fetch_day_mode`）なしに既定で有効化すること
- ❌ 複数リクエストの並列化により実質的なアクセス頻度を上げること
- ❌ robots.txt の確認処理を省略・スキップすること
- ❌ 取得した上映スケジュールを、劇場×日付の一覧として返す API・画面を作ること（利用者向け機能・公開エンドポイントが対象。管理サイト内の抽出検証用表示のみ §1 原則1 の注記・ADR-0015 の条件下で許容）
- ❌ 予約・決済機能を実装すること
- ❌ User-Agent を偽装してブラウザや他サービスになりすますこと
- ❌ 規約確認前（`terms_checked_at` が null / robots_status が unknown）の劇場を `active` にして取込対象にすること

**複数日取得について（ADR-0019・2026-07-25）**: 1ページに1日分しか掲載しないサイト（T・ジョイ梅田等）から複数日を取り込むため、劇場ごとの設定 `fetch_day_mode`（`single` 既定 / `tabs` / `url_template`）で1セッション内に複数ページを取得することを許容する。**「1日1回」の単位はセッション（Cron 1回分の取込）であり、リクエスト数ではない。** 緩めたのは「1セッション＝1リクエスト」という運用上の含意だけで、以下は一切緩めない。

- 各リクエストの間隔は最低5秒（ページ間・日付タブ操作間も同じ。§3）。
- すべて直列。同時に複数ページを開かない・並列化しない。
- 1セッションのリクエスト数は `1 + min(fetch_days, MAX_FETCH_DAYS)` を上限とする（既定 `single` は従来どおり1）。
- `fetch_failed` の Queue 再配信（最大3回。docs/spec/06 §7）を含む1劇場1日の最悪ケースは `(1 + 日数) × 3` リクエスト。`MAX_FETCH_DAYS`=10 のとき最大33リクエスト／劇場／日であり、**これを超える設計（再配信回数や日数上限の引き上げ）は §6 の変更手続きを要する**。
- 人間の閲覧との等価性（原則3）: 日付タブを5秒間隔で順にクリックして見る行為は人間の閲覧の範囲内、という判断に基づく。

これらは §1 の設計原則に基づく。個々の理由は各節を参照。

## 1. 設計原則（不変）

本サービスの合法性・持続可能性は、以下の3原則の同時遵守に依存する。1つでも崩すとリスクの前提が変わる。

### 原則1: 内部利用限定（享受目的でない利用）

取得した上映スケジュールは、**ルート算出ロジックの入力としてのみ使用する**。

- UI に表示してよいのは「算出されたルートに含まれる個別の上映」のみ。
- 劇場や日付を指定してその上映一覧を閲覧する機能は、恒久的にスコープ外（要件 F、API 仕様、画面設計すべてでこれを担保済み）。
- 根拠: 日本の著作権法30条の4（思想・感情の享受を目的としない利用は権利者の許諾なく可能）。スケジュール表そのものを鑑賞・閲覧させる目的ではなく、解析（最適ルート計算）の材料として使う設計であることが、この原則の意味。
- **注記（ADR-0015・2026-07-20）**: 管理サイト（Cloudflare Access 配下・運営者のみ閲覧）の抽出検証用の上映データ表示は、本原則が禁止する「閲覧機能」ではなく §4 の R2 スナップショットと同種の内部利用（検証・デバッグ目的）として許容する。条件: 利用者向け web・公開 API に出さない / SSR 画面のみで機械可読一覧を提供しない / エクスポート・再配信機能を付けない / 画面に検証目的である旨を明記する。日常のスケジュール閲覧用途（享受目的）に常用しない。

### 原則2: 予約は公式へ誘導

- 本サービスは予約・決済・座席選択を一切持たない。
- 各上映には劇場公式ページ（可能なら該当作品ページ）へのリンクを付し、実際の予約・最終確認は公式で行わせる（F-07）。
- これにより「劇場の集客・予約導線を横取りしていない」立て付けを保つ。

### 原則3: 礼儀正しいアクセス

- 事実データ（作品名・時刻・劇場名）は創作性が低く著作物性が争いにくいが、**アクセスの態様**は別問題。過度なアクセスは用途に関わらず業務妨害となりうる。
- 取得頻度・間隔・キャッシュにより、先方サーバーへの負荷を人間の閲覧と同等以下に保つ。
- 1回のセッションで複数ページを取得する場合（複数日取得・ADR-0019）も、間隔・直列・上限（§0・§3）を守り、「人間が同じページを日付タブで順に見る」以上のアクセスにはしない。

## 2. 劇場採用プロセス（取込対象にする前に必ず実施）

新しい劇場を取込対象にする際は、以下を順に実施し `theaters` テーブルに記録する。**1つでも未確認なら `active` にしない。**

| # | 確認事項 | 記録先 |
|---|---|---|
| 1 | robots.txt を取得し、対象 URL パスがクロール拒否されていないか確認 | `robots_status` = allowed/disallowed |
| 2 | サイトの利用規約を確認し、スクレイピング/自動取得を明示禁止していないか確認 | `terms_note` に要点と判断を記録 |
| 3 | 会員登録・ログインなしで対象ページが閲覧できるか確認（ログイン必須ページは対象外） | `terms_note` |
| 4 | 確認日を記録 | `terms_checked_at` |

- `robots_status = disallowed` または規約でスクレイピング明示禁止の劇場は **採用しない**（`retired` として理由を残す）。
- 判断に迷うケース（グレー）は採用を見送る。スモールスタートで無理に対象を広げない。
- `terms_checked_at` から90日を超えた劇場は管理サイトで警告表示し、再確認する（規約は改定されうるため）。
- **コード側の多層防御（人間の運用ミス・レースコンディション対策）**: 「未確認の劇場を active にしない」は運用（人間のプロセス）で担保するのが一次防御だが、取込パイプラインの実行時にも `robots_status='allowed'` かつ `terms_checked_at IS NOT NULL` を検証し、満たさない劇場への fetch は実行前に拒否する（`ingestTheater` 冒頭・docs/spec/09 §5 相当のガード）。加えて cron 実行時は、Queue 投入後〜消費までの間に停止依頼等で `status` が `active` から変わった場合に備え、消費時点で再度 `status='active'` を確認する（`trigger='cron'` のときのみ）。手動取込（`trigger='manual'`）は劇場採用プロセス中の `paused` 劇場を対象にできるため `status` は問わないが、robots/terms のガードは同様に適用する。

### 判断基準の整理（背景知識）

- **ログイン不要で誰でも閲覧できるページ**: 利用規約への「同意クリック」を経ていないため、規約のスクレイピング禁止条項が契約として拘束力を持つとは言いにくい、というのが一般的な整理。ただしこれは「何をしてもよい」ではなく、原則3（アクセス態様）と著作権（原則1で回避）は別途遵守が必要。
- **ログイン後のページ / 会員限定情報**: 規約同意済みとみなされ、禁止条項が有効に働く可能性が高い。→ 対象にしない（確認3）。
- robots.txt でクロール拒否されているパスへのアクセスは、破ると不法行為と評価されるリスクがある。→ 従う（確認1）。

## 3. アクセス制御（技術的遵守）

| 項目 | ルール | 実装箇所 |
|---|---|---|
| リクエスト間隔 | 同一ホストへ最低5秒。Queues のコンシューマ concurrency と delay で担保。**複数日取得（ADR-0019）のページ間・日付タブ操作間も必ず5秒空ける** | ingest ワーカー（`worker/fetch.ts` `HOST_INTERVAL_MS`） |
| 取得頻度 | 1劇場 = **1日1セッション**（翌日以降分の取込）。定時 Cron のみ。1セッションで取得するページ数は `fetch_day_mode` により 1（既定 `single`）〜最大 `MAX_FETCH_DAYS`=10（`tabs`/`url_template`。ADR-0019） | Cron 設定 / `worker/fetch.ts` |
| 1セッションの上限 | `1 + min(fetch_days, MAX_FETCH_DAYS)` リクエスト。`fetch_failed` の Queue 再配信（`max_retries=3`）込みの1日最悪ケースはその3倍。引き上げは §6 の手続きを要する | `worker/fetch.ts` / `wrangler.toml` `max_retries` |
| 並列度 | ホスト単位で直列。異なるホストの並列は可だが、同一チェーン（同一ホスト）は直列化。**複数日取得のページ間も直列**（ループ + 5秒 sleep。ブラウザのタブを同時に開かない） | Queues 設定 / `worker/fetch.ts` |
| 再処理 | 抽出やり直しは R2 スナップショットから。**先方への再アクセスを伴う再取得は fetch_failed 時のみ**。複数日取得の各日スナップショット（`{prefix}_d{date}.html`）からの再抽出も先方アクセスなし | 06_extraction-spec.md §7 |
| User-Agent | 正直に名乗る。連絡先を含める（例: `CinemaHashigoBot/0.1 (+https://<domain>/bot)`）。偽装しない | fetch ヘッダ |
| bot 説明ページ | `/bot` に目的・連絡先・停止依頼方法を掲載 | web |
| タイムアウト | 取得は 30秒でタイムアウト。無限リトライしない | ingest ワーカー |
| キャッシュ | 生 HTML は R2 に保存し、抽出改善時の再取得を不要にする | R2 |

- 停止依頼への対応: 劇場側から取得停止の連絡があれば、当該劇場を即 `paused`/`retired` にする運用を `/bot` ページに明記する。
- **取込 Cron を有効にする環境は常に1つだけ**（ADR-0021・2026-08-14）。「1劇場1日1セッション」は環境をまたいで合算されるため、st と prod で同時に取込 Cron を回すと1日2セッションとなり本ポリシー違反になる。現在は **st のみ有効**（prod は構築保留）。prod を構築する際は st の取込 Cron を停止してから prod を有効化する。
- **User-Agent の実値**（ADR-0021）: 現在は `CinemaHashigoBot/0.1 (+https://cinema-web-st.yuta-develop-ct.workers.dev/bot)`。独自ドメイン取得時に差し替える。到達可能な `/bot` を指していることが要件であり、到達不能なプレースホルダ（`example.com` 等）で運用してはならない。UA 文字列は ingest / api / web の3箇所に重複しているため必ず同時に更新する。

## 4. データの取り扱い

- 保存するのは上映に関する事実データ（劇場名・作品名・時刻・形式・公式URL）のみ。
- 個人情報は取得・保存しない（利用者の個人情報もMVPでは保持しない）。
- 取得した生 HTML（R2 スナップショット）は内部の再抽出・デバッグ目的のみに使用し、外部公開・第三者提供しない。保持期間90日（03_data-model.md §4）。
- 劇場サイトのデザイン・画像・ロゴ等の創作的表現は複製・転載しない（抽出対象は事実データのみ、前処理で画像・スタイルは除去）。
- **抽出プロバイダへの送信（ADR-0011）**: LLM 抽出は前処理済み HTML を外部プロバイダ（既定 Google Gemini）に送信する。既定の Gemini 無料ティアは送信内容がモデル学習に使われうるため、上記「第三者提供しない」と緊張する。以下を条件に許容する:
  - (a) 送信対象は公開ページ（ログイン不要・§2 確認3で担保）の事実データに限る。
  - (b) 前処理で script/style/画像/創作的表現を除去する（§4 上記・06 §2）。
  - (c) 個人情報を含みうるページ（口コミ投稿等）は抽出対象にしない。取込対象はスケジュールページのみ。
  - (d) 機密性の上がるデータを扱う／規模拡大時は、学習不使用の有料ティア or Cloudflare Workers AI（プラットフォーム内完結）へ切替える。切替は抽出クライアントの抽象化により容易。
  - この判断は個人スモールスタート前提。§0/§1 の最重要禁止事項は変更しない。プロバイダ変更で本条件を緩める場合は ADR に記録する（§6）。

## 5. 表示上の遵守（UI）

- 全ページに免責を掲示: 「上映時間は変更される場合があります。必ず各劇場の公式サイトでご確認ください。移動時間・経路は目安です。」（移動時間の文言は非公式経路 API の表示要請への対応。ADR-0014）
- 出典・鮮度の明示: ルート内の各上映に「最終取得日時」を持たせ、古いデータであることが分かるようにする（任意だが推奨）。
- 劇場公式へのリンクは新規タブ・外部リンクとして明示。

## 6. このポリシーを変更する場合

- 本ポリシーの §0・§1 の変更は、サービスの法的前提を変える重大な決定。変更する場合は ADR（docs/decisions/）に理由と共に記録し、必要なら専門家に相談する。
- Claude Code は本ポリシーを緩める方向の変更を自己判断で行わない（§0 再掲）。
