# ADR-0014: 移動時間の解決に ls8h Transit API（無料・非公式）を採用
- Status: Accepted
- Date: 2026-07-13

## Context
P4-6（TravelMatrix 事前計算）は当初 駅すぱあと Web サービスを想定していた（ADR-0005・docs/16 §4.2）が、実質法人向けで個人開発では契約が難しい（オーナー確認）。Google Maps Routes API は TRANSIT 対応だが課金アカウント・コスト監視が前提。`https://api.transit.ls8h.com`（Transit API）は日本全国の GTFS/ODPT 等を統合した無料・認証不要の経路探索 API で、`/api/v1/plan` が geo→geo の door-to-door 所要（accessWalkSecs + durationSecs に egress 含む）・乗換回数・路線名を返す。利用規約はオーナーが 2026-07-13 に実査: 商用利用の禁止条項なし・読み取り専用・禁止は「過度なリクエスト／第三者権利侵害／公式サービスへの誤認表示」のみ。ただし**個人運営**（連絡先が個人メール）で、無保証・予告なき変更/停止が明記された非公式サービスである。

## Decision
移動時間の解決に ls8h Transit API を採用する。運用リスクは以下の3層で吸収する:
1. **KV キャッシュが常時バッファ**: 劇場間は週次バッチ（prod cron 月曜 18:00 UTC + 管理サイトの手動再生成）で `travel-matrix:v1` に事前計算し、planner は実行時に外部 API を呼ばない。生成失敗ペアは**前回値を温存**、全滅時は KV を上書きしない。
2. **フォールバック内蔵**: 行列欠損ペアは従来どおり直線距離推定（docs/05 §5）。API が長期停止しても縮退運用できる（手動固定行列の代替はこのフォールバックが恒久的に担う）。
3. **駅名解決は1回だけ**: origin/destination の未知駅名は `/api/v1/locations/suggest` で座標化し `station-geo:{駅名}`（TTL 30日）へキャッシュ。リクエスト毎の外部呼出は初出の駅名のみ。

取得マナー: 正直 UA・行列生成は直列かつ 1 秒以上間隔（「過度なリクエスト」への配慮）・週次のみ。ToS の表示要請に応じ、web の免責フッターに「移動時間・経路は目安」を追記する。代表時刻は翌日 13:00（昼間ダイヤ）で引く。

## Consequences
- 無料・キー不要のため人間のセットアップ作業（docs/16 §4.2）が不要になる。
- 個人運営 API への依存が生まれるが、参照は週次バッチと初出駅名のみで、利用者リクエスト経路には入らない（KV 経由）。停止時も /plan は最後に生成した行列＋直線距離推定で動き続ける。
- 有料 API（Google Routes 等）への将来差し替えは travel-matrix ビルダーと station-geo リゾルバの2点の差し替えで済む（KV スキーマ＝shared の `TravelMatrix`/`StationGeo` は不変）。
- ODPT 由来データの再配布制限（時刻表データセットとしての再配布禁止）には該当しない: 保存するのは劇場間の所要分と路線名概要のみで、時刻表そのものを持たない。

## Alternatives considered
- **駅すぱあと Web サービス**: 品質・実績は最良だが法人契約の壁（不採用の直接理由）。
- **Google Maps Routes API（TRANSIT）**: SLA ありで信頼できるが、課金設定・コスト監視・キャッシュ制約（Maps ToS のライセンス制限）の確認コストが小規模個人開発に見合わない。API 停止リスクが顕在化した場合の第一候補として温存。
- **手動固定行列の恒久運用**: 5〜10 館なら可能だが更新が人力。直線距離フォールバックとして実質温存されるため、専用実装は持たない。
