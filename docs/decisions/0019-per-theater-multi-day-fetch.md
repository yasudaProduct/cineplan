# ADR-0019: 劇場ごとの複数日取得（日付タブ操作 / URL テンプレート）と、取得マナーの単位を「1日1セッション」に改定
- Status: Accepted
- Date: 2026-07-25

## Context

T・ジョイ梅田（`thr_DYcaApaFD5e7`・tjoy.jp / KINEZO系）の静的 HTML には**当日分の上映しか含まれていない**（2026-07-25 実測: 上映61件・日付見出しなし）。将来日は `<a class="calendar-item js-click-schedule" data-date="2026-07-27">` というタブ（href 無し・10日分）で提示され、クリック時に AJAX がスケジュール領域を差し替える。ブラウザ上では7〜10日先まで表示されているが、`fetch_method=static` の1回のページ取得では当日分しか得られない。

そのため 2026-07-24 の取込は「当日42件 + 先行販売の20件」で成功扱いになり、翌日以降のフルなスケジュールが入らなかった。当初これを「サイトが将来分を未公開」と誤って結論づけたが、実際は**取得方式（static・1ページロード）の限界**だった（オーナーの指摘により判明）。

同型のサイト（1ページ1日分・日付切替がJS、あるいは日付が URL に入る形式）は今後の劇場追加でも現れる見込みであり、T・ジョイ専用の対処ではなく汎用の仕組みが必要。

一方 `docs/08` §0 は「1劇場の日次取得を1回より増やすこと」を禁止しており、この制約に正面から触れる。§6 により ADR での記録が必須（オーナー承認済み・2026-07-25）。

## Decision

1. **劇場マスタに複数日取得の設定を追加**する（migration 0005）。
   - `fetch_day_mode`: `single`（既定・現行動作）/ `tabs`（日付タブを順にクリック）/ `url_template`（`schedule_url` の `{date}` を置換）
   - `fetch_days`: 取得日数。既定 1。`0` = 検出したタブ全件（`tabs` のみ）。
   - `theaters` には 0001 由来のテーブル制約 `CHECK (fetch_method IN ('static','rendered'))` があり SQLite ではテーブル再作成なしに削除できないため、`fetch_method` に値を増やさず**新規カラムで直交に表現**する（「どう描画するか」と「何日分取るか」は別概念でもある）。
2. **`tabs`**: Browser Rendering で1回ページを開き、**構造非依存の汎用タブ検出**（値が `YYYY-MM-DD` に完全一致する属性を持つ表示中の要素を、属性名に依存せず収集）で日付を列挙し、5秒間隔・直列でクリックして日付ごとの DOM を得る。検出0件なら `single` と同じ挙動に自動フォールバックする。
3. **`url_template`**: `schedule_url` の `{date}` を置換し、5秒間隔・直列で日付ごとに静的取得する（ブラウザ不使用）。
4. **コード側の絶対上限 `MAX_FETCH_DAYS = 10`** を `packages/shared` に置き、DB 値に関わらずクランプする。DB の `CHECK`・zod・fetch 実装の**三重**で守る。
5. `docs/08` の「1劇場1日1回」の**単位をリクエストからセッション**（Cron 1回分の取込）に改める。**5秒間隔・直列・並列化禁止・robots/規約ゲートは一切変更しない。** `fetch_failed` の Queue 再配信（`max_retries=3`）込みの1劇場1日の最悪ケースを `(1 + 日数) × 3` と明示し、これを上限とする。
6. R2 は日ごとに `{prefix}_d{date}.html` を保存し、既定文書 `{prefix}.html` も従来どおり残す（既存 run の再抽出互換）。
7. 抽出は文書ごとに日付が既知のため**日付発見コールを省略**し、文書1つにつき日別コールを1回だけ呼ぶ。`text_v3` の日別プロンプトに**基準日として対象日そのものを渡す**と「日付見出しの無い先頭ブロックは基準日の分」という既存の規則がそのまま効くため、**プロンプトの新版は作らない**。

## Consequences

- T・ジョイ梅田は `fetch_method` を `static` → `rendered` に変更する必要がある（タブ操作にブラウザが要る）。Browser Rendering の利用館が1つ増え、コストと所要時間が増える。
- 1劇場1取込あたりの先方アクセスが最大 `1 + 10` リクエスト（間隔待ちで最低約50秒）に増える。Queue 1起動（約15分）に fetch + 抽出を収めるため、pipeline が run 全体の予算から抽出デッドラインを逆算して渡す。
- 抽出の LLM 呼出数は「日数」（日付発見コールが無いぶん単日経路より1回少ない）。無料枠 1,500 req/日 に対して十分小さい。
- 日数が増えると1 run の抽出時間が伸びる。**複数日取得では、1日以上成功していればデッドライン到達で打ち切って部分結果を返す**（未取得日は洗い替え範囲に入らないため既存データは消えない）。単日経路（ADR-0017）の挙動は変更しない。
- 初回の複数日 run は件数が数倍になり V2 `COUNT_ANOMALY` でレビューキューに入る（意図どおりの人間確認。承認すると `succeeded` + `written_count` が記録され以降の平均が追従する）。
- タブ検出の誤検出（日付属性を持つが実際にはタブでない要素）は、クリックしても内容が変わらないためその日を捨てる設計とし、空振り1回のアクセスに留める。タブが日付属性を持たないサイトでは検出0件 → `single` フォールバックで従来動作のまま。

## Alternatives considered

- **サイト内部の AJAX API を直叩き**（T・ジョイの場合 `POST /theaterTop/scheduleGetHtmlApi` に CSRF トークン付きで POST）: 1リクエストで1日分が取得でき最も軽いが、(a) 完全にサイト固有で ADR-0003「構造非依存」に反し他館に再利用できない、(b) 非公開エンドポイント + CSRF トークンの取得は「人間の閲覧と同等」（§1 原則3）という説明が難しい、(c) 予告なく変わる。**不採用**（オーナー判断）。
- **劇場ごとの CSS セレクタ設定（`tab_selector` 列）**: 実装は最も単純で確実だが、ADR-0003 の構造非依存を劇場マスタに持ち込むことになり、サイトのマイナー変更で壊れる設定が館数分増える。**不採用**。
- **`fetch_method` に `rendered_tabs` を追加**: テーブル制約 `CHECK (fetch_method IN (...))` の削除にテーブル全体の再作成が必要（SQLite）。取得方式と取得日数は直交概念でもある。**不採用**（新規カラムで表現）。
- **日付を URL に総当たりで推測**: サイトの URL 仕様に依存し、存在しない日への無駄アクセスが出る。`url_template` は「日付が URL に入ることを確認済みの劇場」に限る明示設定とした。
- **現状維持（当日のみ取込）**: 翌日以降の計画に使えず N-02（前日 06:00 までに対象日のデータ）と `/plan` の実用性を満たせない。**不採用**。
