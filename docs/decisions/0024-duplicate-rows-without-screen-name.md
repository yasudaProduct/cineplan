# ADR-0024: スクリーン名非公開館の同時刻・同作品を V5 の対象外にし、書込前に UNIQUE キーで畳む

- Status: Accepted
- Date: 2026-09-06

## Context

ADR-0023 の修正をデプロイした直後、大阪ステーションシネマのスナップショット再抽出（`run_xaUevVXcVhjx`）を実行したところ、`未定` によるスキーマ失敗は解消し **6日分・413件の抽出に成功した**（`notes` に `2026-09-07: スキーマ不正の1件を除外: screenings[0].startTime="未定"(invalid_string:regex)` が正しく記録されている）。

しかし次段の妥当性検証 V5 で止まった。

```
DUPLICATE_ROW: 重複 2026-09-06|水曜どうでしょう祭UNITE2026 ライブ・ビューイング|17:30|
```

さらに、レビューキューから承認しても反映できない。

原因は同じ1点である。R2 スナップショットの 9/6(日) 列は当該作品のセルに上映時刻を **2つ** 持つ。

```html
<td>
<p>17:30</p>
<p>17:30</p>
</td>
```

ライブ・ビューイングを2スクリーンで並行上映しているためだが、**同館はスクリーン名を公開していない**（この payload の 413行すべて `screenName` が空）。したがって抽出結果としては完全に同一の2行になる。

1. **V5（DUPLICATE_ROW）** が重複と判定 → `validation_failed` → レビューキュー行き。
2. **承認**は payload をそのまま通常書込パスに流すため、`screenings` の `UNIQUE (theater_id, business_date, movie_id, start_at, screen_name)`（migration 0003）に違反する。D1 の `batch()` はアトミックなので**洗い替え全体が落ち**、管理画面には「反映失敗」が出る。ローカル SQLite に同一スキーマを作って2行 INSERT する再現も取った（`UNIQUE constraint failed: screenings.theater_id, screenings.business_date, screenings.movie_id, screenings.start_at, screenings.screen_name`）。

つまり取込も承認もできず、この劇場は詰んだ状態になる。

これは V7 が 2026-07-26 に既に直面した問題と同型である。ADR-0020 は「`screenName` が空文字の劇場は並行上映を1グループに畳んで誤検知するため V7 をスキップし、その劇場群は V2 が主防御になる」と決めた。**V5 には同じ手当てが入っていなかった。**

## Decision

1. **V5 は `screenName` が空文字の行を重複判定の対象外にする。** スクリーン名を公開しない劇場では、同一作品の同時刻上映が正当な並行上映なのか LLM の行重複なのかを抽出結果から区別する情報が無い。V7 と同じ理由・同じ範囲でスキップし、その劇場群は **V2（COUNT_ANOMALY）が主防御**になる。スクリーン名を公開する劇場では V5 は従来どおり全力で効く（そこでの同一キー重複は本物の異常）。
2. **書込前に UNIQUE キー `(theater_id, business_date, movie_id, start_at, screen_name)` で重複行を畳む（先勝ち）。** `replaceScreeningsByDate` で行う。取込・再抽出・レビュー承認の3経路すべてがこの関数を通るため、1か所で塞がる。畳んだ件数は `write.dedup` ログに残す。

## Consequences

- 大阪ステーションシネマの取込が通るようになる。17:30 の2枠は D1 に1行として入る。
- **ルート算出への影響は無い。** 区別できない同時刻・同作品の2上映は、はしご計画上どちらを選んでも等価であり、DP の入力として1行あれば足りる（`docs/spec/05`）。そもそも UNIQUE 制約により DB は2行を保持できない。
- V5 の保護がスクリーン名非公開館で外れる。LLM が行を大量に複製する類の崩れは V2 が拾う（件数が過去平均の 200% を超える）。少数の複製は畳まれて実害なく消える。
- `write.dedup` の件数が普段より急増したら、サイト側の掲載方法の変更か抽出の崩れを疑う手掛かりになる。

## Alternatives considered

- **UNIQUE 制約から `screen_name` を外す / 制約自体を緩める**: 洗い替えの冪等性と、同一上映が二重に入らない保証を失う。制約は正しく、入力側を合わせるべき。不採用。
- **INSERT を `INSERT OR IGNORE` にする**: 畳んだ事実が記録されず、書込件数と抽出件数の乖離を静かに生む。件数を数えてログに残す明示的な dedupe の方が運用上追える。不採用。
- **並行上映を `screenName='1'`,`'2'` のような連番で区別する**: サイトが公開していない情報を創作することになり、`docs/spec/06` の「ページに存在しない情報を補完・創作しない」に反する。不採用。
- **V5 をスキップせず畳むだけにする**: 承認は通るようになるが、毎回 `validation_failed` でレビューキューに溜まり続け、本来見るべき検証NGが埋もれる。不採用。
