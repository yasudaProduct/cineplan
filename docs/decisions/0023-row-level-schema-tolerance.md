# ADR-0023: 抽出のスキーマ NG を行単位で許容し、日別失敗で run 全体を落とさない

- Status: Accepted
- Date: 2026-09-06

## Context

2026-09-06 03:51 JST の大阪ステーションシネマの手動取込が `extraction_failed` で失敗した。調査の結果、ADR-0022 が停止理由とした Gemini 無料枠のクォータ超過（429）とは**別系統**の障害であることが判明した。

エラーは `日別抽出(2026-09-07): 抽出リトライ予算切れ（LLM呼出2回: APIエラー0・出力不正2）: [{"validation":"regex","code":"invalid_string","path":["screenings",0,"startTime"]}]`。`APIエラー0` が示すとおり LLM は2回とも正常に応答しており、落ちたのは zod の `TIME_RE` である。

R2 スナップショット `raw/thr_tHrEbvHueR56/2026-09-06/2026-09-05T18:51:14.568Z.html` を取得して週間表を列ごとに解析したところ、原因が確定した。**同館の `week.html` は上映時刻が未確定のセルに `未定` と書いており**（当該スナップショットに29箇所）、LLM がこれを `startTime` にそのまま載せていた。

| 列 | 上映セル | 非 HH:MM |
|---|---|---|
| 9/5(土) | 69 | 0 |
| 9/6(日) | 66 | 1（idx15 `未定`） |
| **9/7(月)** | **70** | **1（idx0 `未定` = 水曜どうでしょう祭UNITE2026）** |
| 9/8〜9/10 | 各70 | 各1（idx0 `未定`） |
| 9/11(金) | 24 | 24（全部 `未定`） |

9/7 列の非 HH:MM セルはちょうど1件・index 0 で、エラーの `screenings[0]` と完全一致する（この表に colspan/rowspan は無く列対応は一意）。週間表は末尾の日ほど時刻未確定になる構造のため、**この劇場は今後も毎日踏む**。ST の `ingest_runs` では 2026-08-19 以降、同館16 run 中 4 run がこの `startTime` NG で失敗している（成功は3 run のみ）。

プロンプト `text_v3` には「具体的な HH:MM が無い上映は出力せず、notes に記せ」と明示済みだが遵守は不安定で（同一 run 内でも 9/6 列の `未定` は落とせて 9/7 列は落とせていない）、プロンプトだけを防御線にはできない。

調査を難しくした要因が3つあった。

1. **不正値がどこにも残らない。** ZodError の issue は `received` を含まず、`log.ts` のガードレールで LLM 生出力もログ禁止のため、`error_message` からは「何番目の何フィールドか」しか分からない。4回再発しても毎回 R2 を取りに行かないと原因が分からなかった。
2. **リトライが原理的に効かない。** 抽出呼出は `temperature: 0` で、`MALFORMED_OUTPUT_MAX_RETRIES` は検証エラーをプロンプトに戻さず同一プロンプトを再送するだけ。実測でも 09-03・09-06 とも「出力不正2」＝2回とも同じ失敗で、トークンと時間を消費しただけだった。
3. **1セルの不正で run 全体が消える。** `extractDayUnits` は `ExtractionDeadlineError` 以外を rethrow するため、先に成功していた他の日の抽出結果もろとも破棄されていた。

## Decision

1. **zod 検証を行単位で寛容にする。** 封筒（`businessDate` / `notes` / `screenings` が配列であること）は厳格に検証し、`screenings` は要素ごとに検証して NG 行だけを捨てる。捨てた行は理由と実値を `notes` に追記して続行する。封筒 NG のときのみ `extraction_failed`。`packages/shared` に `ExtractionResultLoose` を追加する（スキーマの単一真実は shared のまま）。
2. **エラーメッセージに実値を添える。** `issue.path` から実値を引いて `screenings[0].startTime="未定"` の形にする。`log.ts` のガードレールに従い、当該フィールドの値のみ・40字まで・先頭5件までに制限する。
3. **zod NG をリトライしない。** JSON パース不能（出力の途中切れ）は確率的に起きるため1回のリトライを維持するが、zod NG は temperature 0 では再現するだけなのでリトライしない。予算は種別ごとに独立させる。
4. **日別コールの失敗で run 全体を落とさない。** ある日の抽出が失敗したらその日をスキップして notes に記録し、残りの日を続行する。全日が失敗したときのみ run を失敗とする。**スキップした日は洗い替え範囲から除外する**（`replaceScreeningsByDate` に除外集合を渡す）。含めると DELETE だけされて INSERT が無く、既存データを失うため。

## Consequences

- 大阪ステーションシネマは `未定` セルを含む日も取込が成功するようになる。`未定` の上映は D1 に入らない（時刻が無い上映はルート算出に使えないため、落とすのが正しい）。
- 落とした行は `notes` 経由で `ingest_runs` と管理サイトに残るため、サイト側の表記変更で大量に落ち始めた場合に気付ける。
- **捨てすぎの防御は V2（`COUNT_ANOMALY`）が担う。** 行落としで件数が過去平均の 50% を割れば `validation_failed` としてレビューキューに入り D1 は書き換わらない。したがって「静かに大量欠損したまま洗い替える」ことは起きない。9/11 のように全セルが `未定` の日は 0件 + notes となり、V1 は通るが V2 が拾う。
- 部分成功が許されるようになるため、`ingest_runs.status='succeeded'` は「全日取れた」を意味しなくなる。どの日をスキップしたかは `notes` を見る必要がある。
- zod NG のリトライ廃止で、失敗時の LLM 呼出が1回分減る（無料枠の消費と run 時間の削減にもなる）。

## Alternatives considered

- **`TIME_RE` に `未定` 等を許容する値を足す**: 時刻でない値をスキーマに通すと正規化（`normalizeStart`）が silent に別時刻へ丸める危険がある。分の値域を絞った経緯（`schemas.spec.ts` の回帰テスト）と同じ理由で不採用。
- **プロンプトを text_v4 にして `未定` を名指しで除外させる**: サイトごとの表記（`未定`・`休映`・`—` 等）を列挙し続けることになり、構造非依存という設計目標（`docs/spec/06` 冒頭）に反する。LLM の遵守が不安定であることも実測済み。プロンプト改善は有効だが**防御線にはしない**。行落としと併用はする。
- **リトライ時に検証エラーをプロンプトへ戻して自己修正させる**: 有効だが LLM 呼出が増え、ADR-0022 で調査中の無料枠 TPM 逼迫を悪化させる。行落としで済む問題に呼出を足す判断は今はしない。
- **日別失敗をスキップせず run 全体を失敗させ続ける**: 現状維持。1日の不正で6日分の正しい抽出を捨てるコストが大きく不採用。
