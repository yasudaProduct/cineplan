# ADR-0017: text 抽出を日単位分割呼出（日付発見→日別抽出）に変更
- Status: Accepted
- Date: 2026-07-21

## Context

大阪ステーションシネマ（12スクリーン・`week.html` 週間ページ）は1ページに約347上映（30作品×7日）が掲載され、text 一括抽出（`text_v1`。全日付を1呼出で出力）では出力が推定 約3.5万トークンに達する。ST の succeeded run 実測スループット（`llm_out_tokens` ÷ 所要秒: 96〜190 tok/s。シアターセブン155件=15,728 tok で既に120〜121秒）から逆算すると、最速でも約185秒・典型では約270秒かかり、`llm/gemini.ts` の 120 秒クライアントタイムアウト内に生成が物理的に完了しない。実際に `run_RYyMTKyPoDdg` 等が3回全てタイムアウトで extraction_failed となった（2026-07-20）。入力側のノイズ除去（docs/06 §2-6。27,966→21,407字）は出力律速のため解消にならなかった。

一方、劇場側は無料枠（ADR-0011: 1,500 req/日・15 RPM・1M TPM）で運用しており、呼出「回数」には大きな余裕がある。また Queue consumer は `max_concurrency=1` で全呼出が直列のため、呼出数を増やしても瞬間レート（RPM/TPM）は上がらない。

## Decision

`extract_method='text'` の抽出を、1ページ1呼出から**日単位の分割呼出**に変更する（プロンプト `text_v2`）:

1. **日付発見コール**: ページに掲載されている営業日付の一覧を小出力（`{dates: []}`。shared の `ExtractedDateList`）で取得する。
2. **日別抽出コール**: 発見した各日付 D につき1回「D の上映のみ抽出」を呼び出す（1日 ≒ 50件 ≒ 5千トークン出力 = 30〜60秒/回で確実にタイムアウト内）。
3. 全日の結果を1つの `ExtractionResult` にマージし、書込（`replaceScreeningsByDate`）は従来どおり1回で行う。`ingest_runs` の in/out トークンは全呼出の合算、`prompt_version='text_v2'`。

安全弁として、発見日付は昇順・重複除去のうえ **最大14日** で切詰め、run 内の抽出合計時間に **10分のデッドライン**（各呼出前に判定）を設ける（Queue consumer の実行上限 約15分より内側）。日別呼出の応答に対象日以外の行が混ざった場合は**除外**して notes に記録する（別日への書換はしない）。両呼出のプロンプトは「ページ全文を先頭・タスク指示を末尾」の同一プレフィックス構成とし、将来課金枠に戻した場合の暗黙キャッシュ適用に備える。

vision（月間画像。ADR-0012）は従来どおり1呼出で複数日を抽出する（画像は入力を日別に分けられないため対象外）。`text_v1.ts` はプロンプト版管理規則（docs/06 §4）に従い変更せず残す。

## Consequences

- 出力トークン量が呼出あたり数千に収まり、劇場の掲載件数に依存せず 120 秒タイムアウト内で完了する（シネコン週間ページが取込可能になる）。
- 呼出数は 1+日数（大阪ステーションシネマで8回/取込）。現行4館で 約25回/日・10館全て週間ページでも 約90回/日で、無料枠 1,500 req/日 に対し十分小さい。直列実行のため RPM/TPM への影響もない。
- 入力（ページ全文）を日数分再送するため in トークンは約8倍/取込（大阪ステーションシネマで 約8万 in-tok/run）。docs/06 §8 の日次閾値 500万 in-tok/日 に対して問題ない規模。
- 日付発見コールが日付を誤る可能性が理論上ある（無い日→空振り1回で無害。ある日の見落とし→その日が欠ける。V2 件数検証と管理サイトの抽出検証表示で観測する）。
- 抽出所要時間が伸びる（8呼出 × 30〜60秒 ≒ 4〜8分/run）ため、ストール run 掃除の閾値 `STALE_RUN_MINUTES` を 20分→30分に引き上げる。

## Alternatives considered

- **タイムアウト延長（300秒等）**: 律速は出力生成スループットであり、347件では最速実測でも185秒。将来さらに件数が多いページで再発するうえ、無応答のまま数分待つ接続の安定性リスクが残る。根治にならないため不採用。
- **ストリーミング（streamGenerateContent）**: 総生成時間は変わらず、構造化出力＋現行クライアント実装の作り替えが大きい。不採用。
- **Batch API**: 50%引・別枠レートでレートとタイムアウト問題が同時に消えるが、非同期ジョブ管理（投入→ポーリング）の実装コストが現規模に見合わない。10〜20館規模の夜間一括が主用途になった時点の再検討候補として温存。
- **固定7日窓（今日〜+6日を機械的に7呼出）**: 実装は最小だが、掲載日数に適応できない（殻ページでも7回・2週間掲載の後半を取りこぼす）。日付発見コール方式をユーザーが選択し不採用。
