# Claude Code キックオフプロンプト

> 使い方: 新しいリポジトリ（`docs/` と `CLAUDE.md` を配置済み）のルートで Claude Code を起動し、以下の「貼り付けるプロンプト」全文を最初のメッセージとして送る。以降のセッションは末尾の「2回目以降のプロンプト」を使う。

---

## 貼り付けるプロンプト（1回目 / P0 セットアップ）

```
あなたはこのリポジトリの開発を担当します。まず着手前に、以下を順に読んで全体像と制約を把握してください。

1. CLAUDE.md（最優先。ハードルールとドキュメント索引）
2. docs/README.md（ドキュメント間の優先順位）
3. docs/spec/08_compliance-policy.md（§0 の禁止事項は絶対。特に取得頻度・内部利用限定・予約は公式誘導）
4. docs/plan/01_roadmap.md（フェーズ順とタスク粒度。今回は P0 のみ着手する）
5. docs/spec/12_folder-structure.md（リポジトリ構成のツリー。P0-1 の土台）
6. docs/spec/02_glossary.md（命名はこれが最優先）
7. docs/spec/03_data-model.md と docs/spec/09_d1-implementation.md（P0-3 で使う）
8. docs/spec/04_api-spec.md（P0-2 の zod スキーマ対象）
9. docs/spec/11_environments-deploy.md（P0-4/5/6 の環境・Compose・Actions で使う）

読み終えたら、まず「理解した内容の要約」と「このセッションで実施する P0 タスクの一覧」を提示してください。私が確認するので、承認するまでコードは書かないでください。

■ このセッションのゴール（docs/plan/01_roadmap.md の P0 のみ）
- P0-1 モノレポ初期化（pnpm workspace, packages/{shared,ingest,api,web}。**構成は docs/spec/12_folder-structure.md のツリーに従う**）
- P0-2 shared パッケージの zod スキーマ定義（docs/spec/02, 04, 06 準拠）
- P0-3 D1 セットアップ + マイグレーション（docs/spec/09 §1 の 0001_init.sql をそのまま使用）
- P0-4 Cloudflare リソース定義（3環境 local/st/prod。docs/spec/11 §3 の命名規約と env 分離）
- P0-5 ローカル補助サービス（Docker Compose。docs/spec/11 §2。DB本体は含めない＝D1はwrangler管理）
- P0-6 GitHub Actions（docs/spec/11 §5 の ci / deploy-st / deploy-prod を配置。実デプロイは人間がSecrets設定後）

■ 厳守事項
- P1 以降のタスク（取込・API 本体・DP など）には絶対に着手しない。フェーズの先食いをしない。
- docs/spec/08 §0 の禁止事項に触れる実装をしない。判断に迷ったら実装せず、私に確認する。
- 型は packages/shared に集約し、API/DB/フロントで別定義を作らない。
- 命名は docs/spec/02_glossary.md に従う（Screening/Plan/Leg/Theater。Showtime は使わない）。
- 実際に外部サイトへアクセスするコードは P0 では書かない（P1 の課題）。ローカルは Compose のスタブに向ける。
- シークレットをコードに直書きしない。local は `.dev.vars`（gitignore）、st/prod は `wrangler secret`。ダミー値でも実キーをコミットしない。
- st と prod の Cloudflare リソースID・APIトークンを取り違えない。wrangler.toml の env 分離を守る。

■ 進め方
- タスクごとに「変更予定のファイルと理由」を先に述べ、私の承認を得てから実装する。
- 各タスク完了時に docs/plan/01_roadmap.md の Done 条件を満たしたか自己確認し、結果を報告する。
- コマンド（pnpm/wrangler）を新規に確定したら CLAUDE.md の「コマンド」節を更新する。
- 不明点・ドキュメントの矛盾を見つけたら、実装を止めて指摘する。勝手に解釈で埋めない。

まずは上記 1〜7 を読んだ上で、要約と P0 タスク一覧の提示から始めてください。
```

---

## なぜこの構成か（人間向けメモ）

- **最初にコードを書かせない**: 読解 → 要約 → タスク提示 → 承認、という関門を1つ置くことで、認識ズレを実装前に潰す。Claude Code は放置すると全体を一気に作ろうとするため、スコープを P0 に固定する明示が要。
- **読ませる順序を指定**: CLAUDE.md → README → コンプラ → ロードマップ → 用語 → 該当設計、の順。制約（08）を早い段階で頭に入れさせる。
- **先食い禁止を明記**: フェーズをまたぐ実装を止める。特に「外部サイトへアクセスするコードは P0 で書かない」を釘刺し。
- **矛盾は止めて報告**: ドキュメント間の不整合を勝手に解釈で埋めさせない。

## 2回目以降のプロンプト（フェーズ着手テンプレート）

各フェーズ開始時に、フェーズ番号と参照ドキュメントを差し替えて使う。

```
前回までの成果を踏まえ、docs/plan/01_roadmap.md の 【フェーズID】 に着手します。
着手前に該当ドキュメントを読み直してください:
- 【このフェーズが参照する docs 番号を列挙】
- CLAUDE.md のハードルールと docs/spec/08 §0 は常に有効

このセッションのゴールは 【フェーズID】 のタスクのみです。次フェーズには進まないでください。

まず「実施するタスク一覧」と「変更予定ファイル」を提示してください。承認するまでコードは書かないこと。
タスクごとに Done 条件（docs/plan/01_roadmap.md 記載）を満たしたか報告してください。
```

### P2 着手時の特記（重要）

P2 のプロンプトには次の一文を必ず加える:

```
docs/spec/10_dp-implementation.md §7 の期待値テスト（検算済み）を最初に実装し、
それが全て緑になるまで P2 の他タスクに進まないでください。
期待値の数値は変更しないこと。実装が合わない場合は実装を直してください。
仕様側の誤りを見つけた場合は、実装を止めて私に報告してください。
```

## 運用のコツ（人間向け）

1. **1セッション1フェーズ**を厳守する。詰め込むと Claude Code のコンテキストが膨らみ精度が落ちる。
2. 承認関門では、提示されたタスク一覧が docs のスコープと一致しているかを必ず目視する。ズレていたらこの場で正す。
3. P2 の期待値テストが緑になった時点で、一度自分でも `spec/10 §7` の数値と突き合わせる。ここがサービスの正しさの基準点。
4. スキーマ変更が発生したら、Claude Code に「まず docs と packages/shared を直してから実装」の順序を守らせる。実装だけ先に変えさせない。
5. 各セッションの終わりに CLAUDE.md のコマンド節・進捗が更新されているか確認する。
